## Three open items

### 1. Is `FIRECRAWL_API_KEY` scoped to Preview, or only Production?

**The blocking question.** The suspicion is that the preview deployment has no
page reader at all, which would make every JavaScript-rendered site report "no
menu" — exactly the failure this PR exists to kill, and no code change would fix
it. Lina Stores and NENI are precisely those sites.

```bash
npx vercel env ls        # names + environments, no values revealed
```

Look at the `FIRECRAWL_API_KEY` row's Environments column. If Preview is
missing:

```bash
npx vercel env add FIRECRAWL_API_KEY preview   # value on stdin
```

Env changes only take effect on the **next** deployment, so redeploy after.

If Preview *is* already ticked, it is a real bug — diagnose with that ruled out.

### 2. Apply the `ai_usage_log.source` migration

`supabase/migrations/20260806120000_ai_usage_log_source.sql` adds
`source` (`product` | `qa`) so the ledger can separate what serving users costs
from what testing costs. Both are real spend; they answer different questions.

Not applied — the cloud session had no route to Supabase. The direct DB
connection is blocked in that sandbox too; see CLAUDE.md for the Management API
method, or just run it from a machine with `psql`/dashboard access.

`logUsage` retries without the column if it is absent, so nothing is lost while
this is pending — but the label is meaningless until it runs.

### 3. The cloud clone rolled back twice

The container's git checkout silently reverted to an older commit twice during
this work. The first merge attempt would have destroyed six commits; the remote
had everything, so nothing was lost. Almost certainly sandbox-specific, but the
habit it taught is cheap:

```bash
git fetch origin <branch> && git log --oneline HEAD..FETCH_HEAD   # empty = safe
```
